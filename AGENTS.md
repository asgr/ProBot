## Project: ProBot R Package (torch-based ML)

Three model types: **MDN**, **Point** (deterministic regression), and **Normalizing Flow**.

### Package structure

#### Shared utilities
- **Trainers split off a verification set by default (0.9.0, 2026-09-13).** All three of `probotTrainMDN/Point/Flow()` gained `holdout_fraction = 0.1, val_dataloader = NULL, val_batch = NULL, split_seed = NULL, holdout_stop = TRUE, holdout_min_delta = 1e-3, holdout_patience = 5L`, appended after `stop_delta` so no existing positional binding shifts (the 4-safe-argument convention is unchanged; every new arg must be named). `.probotValSetup()` (in `R/probotUtils.R`) is called by all three **before epoch 1** and is also where a non-dataloader `dataloader` is rejected — without that guard, passing a matrix surfaces as "`$ operator is invalid for atomic vectors`". `val_dataloader` takes precedence over `holdout_fraction`; `holdout_fraction = 0` restores the exact pre-0.9.0 behaviour (`epoch, loss, ...` only, `res$validation` NULL); fewer than 10 rows **warns and skips** the split rather than trending a useless set. `.probotSplitLoaders()` slices `dataloader$dataset$tensors` with `index_select()`, so **the index tensor must be built on the data's own device** (`device = t$device`) — across devices the MPS backend aborts the process with "Placeholder storage has not been allocated on MPS device!" instead of raising an R error, which is why `test-probotTrainHoldout.R` carries a deliberately non-CPU test (it fails against a CPU-index build). The verify loader is always `shuffle = FALSE, drop_last = FALSE` so cross-epoch trends are real; the train loader inherits batch size/shuffle/drop_last. **A split re-indexes the training rows, so a run with a holdout is NOT numerically identical to `holdout_fraction = 0` at the same seed**, and an unseeded split consumes one draw from R's global RNG (`.probotWithSeed()` restores the stream when `split_seed` is given).

  `history` gains `val_loss`, plus `val_mae`/`val_rmse` **only when the trainer's `lambda > 0`** (the unblended loss has no point estimate to take an error of). The holdout is scored by `.probotValScorer(model_type, loss_fn, lambda, point, n_point_samples)` with the **same blend as training** — a pure-NLL verify number beside a blended train number would make the stop rule compare incomparable trends, so an MDN at `lambda = 0.7` shows a `val_loss` well below `probotLossEval()`'s pure value (verified: blend == `0.3*pure + 0.7*mse` to 1e-4). At `lambda = 0` the column matches `probotLossEval(input, output, model, idx = validation$verify_idx)` **exactly** (0.0 diff on Point and RealNVP), which is the cross-check the tests use — `probotLossEval()` is an independent path (R matrices, own batching, its own `eval()`/restore). Scoring deliberately does **not** reuse `probotLossEval()`: it round-trips through CPU matrices, which is fine once but not every epoch for tensors already on the device. `.probotValScore()` iterates the loader (not manual `narrow()`) and restores the prior train/eval mode via `on.exit()`.

  Two independent early-stop rules, both gated by `early_stop`. The pre-existing one compares rolling means of the **train** loss (`stop_window`/`stop_delta`) and reports `stop_reason = "train_loss_plateau"`. The new one is `.probotHoldoutStop()`, reporting `"holdout_overfit"`: it fires only on the **asymmetric** signal — train still falling (`< -stop_delta/2` per epoch) **while** verify flattens or rises (`> -holdout_min_delta`) — so a model that has converged (train flat, verify rising) is left to the plateau rule, which is the correct diagnosis there and was observed on a real 500-row run. Both halves read `.probotTrend()`, a least-squares slope over the last `stop_window` epochs, so a trend of `delta` per epoch is detected at any window length (do **not** "simplify" it back to a window-mean difference, which rescales with the window). Below 4 points a slope is meaningless so the test degrades to "neither is moving"; `holdout_patience` counts consecutive flagged epochs. `stop_delta/2` as the train threshold is deliberate — making it equal to `stop_delta` lets the two rules fight over the same epoch and neither says anything. The loop also fixes the documented NaN trap by guarding `improvement` with `is.finite()` instead of letting `if (NaN > 0 & ...)` throw "missing value where TRUE/FALSE needed". **The returned model is the one at the stopping epoch, not the best one** — `validation$best_epoch`/`best_val_loss` name the better one; there is still no best-checkpoint restoration.

  Verbose output names both numbers so they cannot be misread: `Epoch 20 Train Loss 0.242455 | Verify Loss 0.149282 (50 rows)  MAE ... `, with a one-time `Split 450 train / 50 verify rows (holdout_fraction = 0.1)` banner. `.probotEpochLine()` keeps the MDN arm's original 3-decimal formatting (detected via `metrics$sigma`/`mix`, not a passed flag) and only appends `| Verify MAE/RMSE` when the blend is active.

  **Resuming a run broke** once the split landed: `.probotTrainLoop()` used base `rbind(history, history_df)`, which requires identical columns, so continuing a `holdout_fraction = 0` history with a default run died with "numbers of columns of arguments do not match" — an error naming neither cause nor column. `.probotBindHistory()` now unions the columns and fills the absent ones with `NA`, which is the honest reading (that epoch has no verification number). Verified both directions: mixed-schema resume yields 4 `NA`s then real values, and a no-split-into-no-split resume keeps the exact 4-column schema with no `NA`s.

Overfitting is **not** reproducible with a clean learnable signal — train and verify then fall together, so a test built that way passes vacuously. The recipe in `.make_overfit_data()` (`tests/testthat/test-probotTrainHoldout.R`) is signal **plus per-row irreducible noise**, which the net memorises; `stop_delta = 1e-12` is then needed to keep the plateau rule from firing first. That file is 29 tests / 144 expectations. `test-probotFlowLoc.R`'s "lambda = 0 keeps the (epoch, loss) schema" assertion now passes `holdout_fraction = 0`, since the claim under test is the absence of `mae`/`rmse`, not of `val_loss`. `R CMD check` on 0.9.0: examples OK, two `inst/doc` WARNINGs are the `--no-build-vignettes` artifacts, and the `self` NOTE is the pre-existing torch `nn_module` one.

- **R/probotLoss.R** — `probotLossMDN`, `probotLossNF`, `probotLossMSE`, `probotLossMAE`, `probotLossMAPE`, `probotLossHuber`

- **`probotLossNF()` had an (N, N) broadcast (0.9.1, 2026-09-14).** It built `log_p_z` with `$sum(dim = 2)$unsqueeze(1)` — a **(1, N) row** — and added the model's **(N, 1)** `log_det_jac`, so their "per-row log-likelihood" was an **N×N matrix** whose element `[i, j]` pairs row *j*'s base density with row *i*'s Jacobian. Fixed by `$sum(dim = 2, keepdim = TRUE)`; the per-row term now lives in `.probotNFLogLik(out)` purely so the **(N, 1) shape is assertable**, since no value test can catch this. **Both the reported scalar (in exact arithmetic) and the gradients are identical either way**: `mean_{i,j}(a_j + b_i) == mean_i(a_i + b_i)`, and `d/dtheta_k` of the broadcast mean picks out `(1/N)(da_k + db_k)` — so *training was never corrupted*, only the *number*. The failure mode is size alone: at N = 90 000 that is 8.1e9 float32 = **30.2 GB, above the 2^31 element count**, where the add/mean goes wrong (int32 indexing is the prime suspect, but which of overflow vs summation error was not isolated). Symptom that identifies it: a holdout scored in **one** batch reported `+223` for a model whose true verify NLL (same rows, at batch 4096) is **-13.5** — train −13.47 vs verify +223 *looks* like catastrophic overfitting, and `best_epoch = 1` looks like divergence, but neither is a generalization statement. Diagnose by scoring the same rows at two batch sizes: **if the number moves with batch size, it is not overfitting.** Also rule out `train()`/`eval()` asymmetry by checking for BatchNorm/dropout — there is **none** in any flow style, so `model$eval()` in `.probotValScore()` is a no-op.
- **The verify batch is capped at 4096, not the whole holdout.** `.probotSplitLoaders()` used `val_batch = n_val`, which is what handed `probotLossNF` a 90 000-row batch. Now `min(n_val, 4096L)`, matching `probotLossEval()`'s default batch so the two independent scoring paths stay comparable; an explicit `val_batch` still wins. Defence in depth — a user-supplied `loss_fn` may also build a batch-quadratic intermediate. `man/probotTrain{Flow,MDN,Point}.Rd` previously claimed the verification loss "is identical for any `val_batch`", which is exactly the assumption this broke; wording now says so with the caveat.
- **A spurious `holdout_overfit` stop was latent in this**: the bogus verify number rises, so with the default `early_stop = TRUE, holdout_stop = TRUE` a flow run stops within a few epochs and reports the *best* verify epoch as epoch 1 (the untrained model). The ProSpect MAF tutorial escaped it only because it passes `early_stop = FALSE`.

- **`mdn_components` is no longer an argument anywhere a model is in scope (0.8.0, 2026-09-12).** Removed from `probotLossMDN/MSE/MAE/MAPE/Huber` (third arg is now `model`, mirroring `probotLossNF`), `probotSingleEpochMDN`, `probotTrainMDN`, `probotPredictMDN`, `probotSamplePostMDN`, `probotPIT`, `probotTARP`, `probotCRPS`, `.probotPostSampler()`, `.probotChunkApply()`, `probotLossEval()` and `.probotLossEvalRows()`. It stays a `probotMakeMDN()` constructor arg, a stored `model$mdn_components`, a checkpoint metadata key, and a `probotNetworkSuggest()` output field — those are where the number *originates*, and 0.7.0's save/load machinery depends on them. The K/D split is genuinely ambiguous from the head width alone (25 units is K=5,D=2 or K=1,D=12), so a single resolver reads it off the object: **`.probotMDNK(model, output_features)`** in `R/probotNetworkMDN.R`, used by `.probotUnpackMDN(output, model)`. Precedence, each step selecting one of the factorisations enumerated by `.probotMDNSplits(rows)`: (1) stored `mdn_components` **and** `output_dim` together, but only if `K*(2D+1) == rows`, else "internally inconsistent"; (2) `mdn_components` alone, matched against the candidate Ks; (3) `output_dim` alone, matched against the candidate Ds; (4) a unique factorisation (rows=3 must be K=1,D=1 — this is what keeps hand-built stub modules in the test suite working); otherwise an error **listing every candidate split**. Do not "simplify" this to `model$mdn_components %||% guess`: the K=1/D=12 vs K=5/D=2 case is why the enumeration is load-bearing, and `.probotMDNK(3, 15)` deliberately errors naming `mdn_components` because a bare number reaching here is a leftover positional. `probotLossMDN`/`.probotLossEvalRows` take K from `p$mu$size(2)` after unpacking rather than re-resolving it.

  **Every removal silently shifts a later argument up a slot, and four of those shifts are silent rather than noisy** — hence the guards, which exist because a wrong-but-plausible number is worse than an error: `probotSamplePostMDN(x, model, 5)` would have returned *five draws* (count → `n_samples`), and `probotLossEval(x, y, mdl, 3)` would have quietly scored only row 3 (count → `idx`). Guarded by `.probotPositionalLimit()`: `probotSamplePostMDN`/`probotPredictMDN` (2 safe), `probotLossEval` (3), `probotSave` (4). Named-but-positionally-shifted cases are caught by type instead: `probotSingleEpochMDN`/`probotTrainMDN` via `.probotCheckLossFn()`, the assess trio via `.probotNParams()`, and `.probotMDNK()` itself rejects an atomic `model`. A retired *named* argument (`mdn_components = 3`) now fails with R's own "unused argument", which is clear enough not to need a handler. `probotSave()`'s `model_type`-then-positional contract is unchanged.

  Two things learned the hard way while writing `.probotNPositional()`. **(a) `match.call()` cannot be used to count positional arguments** — it resolves them to their formal names, erasing exactly the information being counted. **(b) `names(sys.call())` has one entry per element *including the function name in slot 1*, and that slot is always `""`**, so `sum(nm == "")` over-counts by one whenever a call mixes positional and named arguments. **This was a live bug in the 0.7.0 `probotSave()` guard**: `probotSave(m, o, f, "point", col_means = cm)` — four positional, entirely legal — was reported as "passed 5 by position" and refused. It shipped unnoticed because the 0.7.0 test only used all-positional and all-named calls, where the two formulas agree. The fix (`(snm == "" | is.na(snm))[-1L]`) is pinned by new cases in `test-probotIO.R` that mix positional with named. When `names()` is `NULL` (no argument named at all) the count is `length(call) - 1`, and `%in% NULL` being always FALSE means that branch must be tested with `is.null()`.
- **R/probotLossEval.R** — `probotLossEval(input, output, model, idx = NULL, batch = 4096, loss_fn = NULL, device = NULL, verbose = FALSE, per_row = FALSE)` scores a trained model's loss on plain R matrices/data frames (or tensors) with **no gradients and no parameter changes**, for held-out / overfitting checks. Takes **context first, targets second** like `probotDataLoader()` — the *reverse* of the `probotLoss*()` functions, whose first arg is `output_true`; the stored `input_dim`/`output_dim` are checked against the column counts and the error names the swap. Type comes from `.probotModelClassType()`, so it covers MDN, Point, all three flow styles and `probotFlowLoc`. Defaults mirror the trainers so the number equals their reported epoch loss: `probotLossMDN` / `nnf_mse_loss(pred, true)` / `probotLossNF` (the MDN loss takes `model`, not a component count). Returns `list(loss, n, batches, model_type, loss_name)`; `loss` is the **row-weighted** mean per-row loss (`nnf_mse_loss` itself averages over *elements*, so Point is only per-row when head width == target width, which the guard enforces). `probotLossEval()` no longer takes `mdn_components` at all (0.8.0) — the count comes from the model, so one set of leading arguments scores every arm of a model comparison, and a custom `loss_fn` for an MDN or flow must accept `model =`. Placed in `eval()` for the pass and restored to its prior mode via `on.exit()`. `device` defaults to the model's own. Tests in `tests/testthat/test-probotLossEval.R`; docs in `man/probotLossEval.Rd`. **`per_row = FALSE` (2026-09-12)** adds `per_row = TRUE`, which appends `.probotLossEvalRows()`'s `row_loss` plus `.probotLossEvalSummary()`'s `loss_median`, `loss_p90`, `loss_max`, `loss_mad`, `extreme_threshold`, `n_extreme` (flag = row above median + 10 MADs, MAD rescaled by 1.4826). Motivation: NLL is unbounded above, so a single tail row can wreck the headline mean while leaving the median untouched; splitting a flow's loss into `0.5*(||z||^2 + D*log(2*pi))` and `-log_det_jac` also separates a genuine density failure from a Jacobian failure, which the scalar cannot. Only offered for a model type's **default** loss (`identical(loss_fn, default_loss)`) — a custom `loss_fn` may aggregate with no row-level analogue, so `per_row = TRUE` warns and omits the summary. Point and MDN reuse the forward pass already done for the scalar; a flow must run `model$forward(yb, xb)` a second time because `probotLossNF` returns only the scalar, which is why this stays opt-in. The MDN branch clamps `log10_sigma` to `[-5, 5]` and uses the **clamped** value in both `sigma` and the log-normalisation, exactly as `probotLossMDN` does; using the raw value agrees in easy cases and silently diverges once the clamp binds. With `per_row = FALSE` the result is exactly the pre-existing five fields, so `expect_named()` callers are unaffected. Note the helper converts input via CPU and re-places it on the resolved device, so callers may pass plain R matrices — but a test that compares against a *direct* `model(x)` call must build its tensors on `model$parameters[[1]]$device`, since the constructors auto-place on MPS.
- **R/probotAssess.R** — `probotPIT(input, model, params, ...)`, `probotTARP(...)`, `probotCRPS(...)`. All three are **model-agnostic**: `.probotPostSampler()` checks `inherits(model, .probotFlowClasses)` (`probotFlowRealNVP`/`probotFlowMAF`/`probotFlowNSF`/`probotFlowLoc`) and dispatches to `probotSamplePostNF()`, otherwise to `probotSamplePostMDN()`. The signature is **identical for both families** — nothing describes the posterior shape by hand since 0.8.0. `params` is validated by `.probotNParams()` *before* `.probotNTest()`, because `params` is the third formal and a legacy positional `mdn_components` lands there (`ncol()` of a scalar is `NULL`, which otherwise surfaces as a confusing "arguments imply differing" error from the dimension guard). `params` must have as many columns as the sampler's `D` — `.probotChunkApply()` guards this and errors with "dimensions", which is the only way to catch a *flow* mismatch (a truncated `params` for a flow otherwise fails inside torch's broadcasting first). All three default to `n_test = NULL` (= all rows of `params`; `probotTARP` previously defaulted to `1e4` and silently truncated). `n_test = 0` returns an empty result. Sampling is chunked via `.probotChunkApply()` (callback per observation chunk) + `.probotNTest()`, so peak memory tracks `batch_size * n_samples * D` rather than `n_test * n_samples * D`. `batch_size = NULL` sizes chunks to ~2e6 draw rows. `verbose` prints from **`.probotChunkApply()`'s own loop** (labelled via its `label` argument, e.g. `"probotPIT: chunk 3/14 (obs 7-9 of 40)"`), and the samplers are called with `verbose = FALSE` — the outer loop always passes `batch_size = length(rows)`, so an inner report would be a constant, useless "chunk 1/1". At most ~20 lines, plus first and last. `input` may be a bare vector (one observation) — must NOT go through `as.matrix()`, which orients a vector as a column; errors if `nrow(input) < n_test`. Per-chunk statistics are **vectorised over the whole chunk** (no per-observation R loop, `.probotObsDraws()` is gone): draws are flattened `(S, D*K)` and compared against `as.vector(t(params[rows, ]))`, which is the matching column order because `matrix(array)` keeps the parameter axis fastest. Two traps in that maths: the PIT/CRPS results must be reshaped with `t(matrix(..., nrow = n_params))` before assigning to `pit[rows, ]`, and TARP's per-observation thresholds need `matrix(rep(truth_proj, each = n_samples), ...)` — `matrix(truth_proj, nrow = n_samples)` silently *recycles* the vector down the chunk, comparing every observation against the wrong truth (this was a real bug in an early draft; caught by hand-computed directions, not by a same-seed comparison against the old loop, because the directions are drawn after the sampler consumes RNG)


#### MDN model
- **R/probotNetworkMDN.R** — `probotMakeMDN()` constructs nn_module; `.probotUnpackMDN(output, model)` splits the output tensor into mu/log10_sigma/logits, resolving the head width into (K, D) via `.probotMDNK()`; `.probotMDNSplits(rows)` enumerates every valid factorisation and is what makes an ambiguous width an error rather than a guess
- **R/probotPredictMDN.R** — `probotPredictMDN()` (auto-device from model), `probotSamplePostMDN()`, `probotMarginalPostMDN()` (aggregates posterior mean/SD analytically). `probotSamplePostMDN(input, model, n_samples = 5000, col_means = NULL, col_sds = NULL, col_names = NULL, device = NULL, batch_size = NULL, verbose = FALSE)` now mirrors `probotSamplePostNF()`: it runs the forward pass itself instead of accepting a precomputed `mdn_output` + `index`. The mixture count is read off the unpacked head (`K <- dim(mu)[2]`) rather than passed. Vector or 1-row matrix -> `(n_samples, D)` matrix; multi-row matrix -> `(n_samples, D, N_obs)` array chunked by `batch_size` (same ~2e6-row default as the NF sampler). `col_means`/`col_sds` are optional and must be given together — omitted, samples come back on the *scaled* output scale (unlike the older always-unscaled behaviour). Mixture maths is done R-side on per-chunk arrays (only `(B, K, D)` tensors cross to R). Both posterior functions soft-clamp `log10_sigma` to `[-5, 5]` before exponentiating, matching the clamp in `probotLossMDN`/training — samples/SDs are capped at sigma = 1e5, unlike the older raw `10^log10_sigma` path. `probotSamplePostMDN()` is reproducible: all its randomness is the R global RNG (`sample.int()` for component draws, `rnorm()` for the Gaussian draws), so `set.seed()` before a call reproduces samples exactly. Reproducibility is however **chunk-size dependent**: draws are consumed jointly across a chunk's observations, so the same seed yields different numbers for `batch_size = 1` vs `batch_size = 10`. Under `batch_size = 1`, observation *k*'s draws are identical to a single-observation call made at seed + (k-1) `sample.int(n_samples)` consumptions — that is the only exact cross-call equality available. The earlier "nondeterministic sampler" note was just unseeded R RNG, not a bug. Use `set.seed()` (or the analytic CRPS reference) rather than sample-level equality in tests; for distributional assertions compare against `probotMarginalPostMDN()` moments with tolerances derived from MC standard error (fixed relative `tolerance` is meaningless when the analytic mean is ~0).

- **R/probotTrainMDN.R** — `probotSingleEpochMDN()` with manual gradient clipping (`torch_clamp`, value=1) and optional MSE blend (`lambda`); `probotTrainMDN()` wrapper

#### Normalizing Flow model
- **R/probotNetworkFlow.R** — Three architectures, all `nn_module`s sharing the `input_dim, output_dim, ..., device=NULL` convention (`input_dim` = conditioning context, `output_dim` = parameter space):
  - `.probotRealNVPLayer()` / `probotFlowRealNVP(input_dim, output_dim, n_layers = 4, hidden_dim = 32, soft_clamp = 3)` — affine coupling, soft-tanh-clamped `log_scale`, halves swapped each layer
  - `.probotMAFBlock()` / `.probotMaskedLinear()` / `.probotPermutationLayer()` / `probotFlowMAF(input_dim, output_dim, n_blocks = 5, n_layers_per_block = 2, hidden_dim = 500, soft_clamp = 3)` — MADE-masked autoregressive blocks with permutation layers between them (not after the last)
  - `.probotRationalQuadraticSpline()` / `.probotSplineCouplingLayer()` / `probotFlowNSF(input_dim, output_dim, n_layers = 4, hidden_dim = 32, n_bins = 8, tail_bound = 3)` — rational-quadratic spline coupling. Both coupling styles require `output_dim >= 2`. `.probotRationalQuadraticSpline()` is the identity outside `[-tail_bound, tail_bound]` via `torch_where`; because `torch_where`'s autograd multiplies the *unselected* branch by zero and `0 * NaN = NaN`, the input is clamped into-domain (`ic`) before bin selection/polynomial evaluation — otherwise an empty bin mask yields 0/0 -> NaN in the unselected branch and poisons all gradients (forward still prints finite, so the bug only appears after `backward()`)
  - **Bin selection counts edges (`sum(coordinate <= ic)`), it does not test an interval.** The interval mask `(ic >= coord) & (ic < coord + span)` was wrong in float32: `coord[[k]] + span[[k]]` (an addition) and `coord[[k + 1]]` (a cumsum) disagree by up to an ulp. Over 2.1M coupling-layer-style internal knots, **23.6% gapped** (zero bins matched -> the old `ones_like()` fallback then summed *all* K bins) and **23.6% overlapped** (two bins summed). Either way `select_bin()`'s masked sum returned adjacent bins added together, so `theta` escaped [0,1], the polynomial denominator went negative, and `log()` of it was NaN — this was the cause of the transient NaN loss epochs in NSF training (11 of 15 benchmark runs; e.g. `nsf`/seed 303 at epochs 10,23,32,40,48,53). The `ones_like` fallback and a `torch_clamp(bin_index, 1, n_bins)` are both **unreachable and removed**: `coordinate[[1]] == -tail_bound <= ic` by construction of the clamp, so the count is >= 1, and with K edges it is <= K. Measured over 6e5 probes on every knot/right-edge/±1ulp/both bounds: count spans exactly 1..K. Only a NaN input escapes (all comparisons FALSE), and its output is NaN either way. Regression test: `"rational quadratic spline selects exactly one bin at every knot"` in `tests/testthat/test-probotNetwork.R` — it fails hard against the old code (72+ failures, up to 396 non-finite `logabsdet` at one knot) and passes against the new. **It is float32-only by design; do not convert it to float64, where both implementations pass.** `torch_arange(1, K, dtype = float)` is endpoint-inclusive, so the last bin remains selectable.
  - **A NaN *forward* in the spline does not imply NaN *gradients*, which is why those runs self-healed.** `d/dx log(x) = 1/x` is finite at negative `x`, and `mean()` spreads a finite 1/N contribution, so the bad element perturbed the loss without poisoning it: all 31 recoverable NaN epochs continued finite the next epoch, all 18 saved checkpoints had zero NaN/Inf parameters, and the final `nsf_101` weights give no NaN on any of the 100k training rows. Measured directly: at knots the old code produced 1169 non-finite `logabsdet` values but **0 non-finite gradients out of 257,600**. Consequence: a gradient-finiteness test at knots is *not* a regression test for this bug — it passes under both implementations. Test the forward values instead. Related trap in `.probotTrainLoop()`: with `early_stop = TRUE`, a NaN epoch makes `improvement` NaN and `if (improvement > 0 & improvement < stop_delta)` throws "missing value where TRUE/FALSE needed" (reproduced). The benchmark arms escaped this only because they pass `early_stop = FALSE`. There is still no best-checkpoint selection, so a run ending on NaN reported `final loss NaN`.
  - **The inverse's quadratic denominator must be `-(b + sqrt(disc))`, NOT `-(torch_abs(b) + sqrt(disc))`.** The `abs()` form silently selects the *other* root whenever `b < 0`, giving order-1 (not precision-level) error. `b >= 0` for a freshly-initialised conditioner, so every existing round-trip test passed with the bug present — a default-model round-trip *cannot* catch this class of error. Verified against `uniroot` on the forward map (independent of the algebra): `abs()` errs up to 5.9 when `b<0` (2–30% of entries), the correct form to 4e-15. On the real `prospect_flow_nsf.pt` (11 layers, d=9, hidden=512) this fix moves the `forward->inverse` round trip from **61.8% -> 7.2%** of entries above 1e-3, mean 0.30 -> 3.2e-3
  - **The residual ~5% float32 round-trip error on that checkpoint is NOT a bug — it is inverse conditioning, and it is expected.** In float64 on the real weights the same model round-trips to **max 2.1e-07, 0% bad**. Do not chase it as a third defect. Mechanism: the trained splines' derivative dynamic range is ~1.6e4 (min 1e-3, max ~16) and `b + sqrt(disc)` is a cancelling branch, so float32 loses the root across an 11-layer composition; `min|denom|` observed is ~5e-2, so no division-by-zero is ever reached. Consequence for practice: `probotSamplePostNF()` on an NSF is a float32 approximation whose error concentrates near bin boundaries; `probotPIT`/`probotCRPS`/`probotTARP` scores are unaffected in practice because they average over `n_samples` draws.
  - **Do not re-add "defensive" guards here.** A zero-denominator substitution and a `root <- torch_clamp(root, 0, 1)` were tried and removed: `denom == 0` is *provably unreachable* (since `a + b == heights^2/widths > 0`, `b <= 0` forces `a > 0`, so `denom = 0` needs `c = 0`, which then makes `b > 0` — contradiction), and all three ablations (bare / +guard / +guard+clamp) gave byte-identical results on the real checkpoint. The root clamp also binds on only 0.07% of float32 entries and fixes none of the 4.9% error, so it masks nothing useful. Prefer deleting the wrong `abs()` over wrapping it in mitigation.
  - **Gradient NaNs through the NSF *inverse* at `params * 4` or `* 8` are pre-existing** (48/1800 at scale 4, 3/1800 at scale 8, zero at scale 1) and identical in the original and fixed code — they are not caused by, and are not addressed by, the root fix. Untested/unsolved; note that a blanket `p$mul_(scale)` across *all* parameters is a far more extreme regime than any trained model (it reaches derivative range 3.6e5 vs the real checkpoint's 1.6e4), which is why early synthetic sweeps at scale >= 3 looked like a second bug when they were an artifact of the test.
  - `probotMakeFlow(input_dim, output_dim, ..., style = "realnvp" | "maf" | "nsf")` is a **facade returning a zero-arg constructor**, exactly like `probotMakeMDN()`/`probotMakePoint()` — always call it as `probotMakeFlow(...)()` (this is also what `probotLoad()` does). Returning an instantiated module instead silently breaks `probotLoad()` for every flow checkpoint. `n_blocks` defaults to `NULL` and, for `style = "maf"`, falls back to `n_layers` (`maf_blocks <- if (!is.null(n_blocks)) n_blocks else n_layers`), so a `probotNetworkSuggest()` depth pipes straight in; an explicit `n_blocks` wins. `n_layers_per_block = 2` is hardcoded in the facade
  - Renamed symbols to watch for in older notes/vignettes: `probotFlowCouple` -> `probotFlowRealNVP`, `probotFlowAutoReg` -> `probotFlowMAF`, `probotCouplingLayer` -> `.probotRealNVPLayer`, `dim_x`/`dim_theta` -> `input_dim`/`output_dim` (commit `866799a` also **swapped the positional order**, so translate old `(dim_theta, dim_x)` calls to `(input_dim, output_dim)`). Validate vignette/API claims against the source tree via `pkgload::load_all()`, never the installed library, which lags and carries the old names
  - **`probotFlowLoc(base_flow, input_dim, output_dim, loc_hidden_dims = c(128, 128), device = NULL)`** (R/probotNetworkFlow.R) is a *fourth* `nn_module`: a residual location head wrapping any of the three styles as `theta = mu(x) + f_inverse(z, x)`, `z ~ N(0,I)`, where `mu` is an MLP of `nn_linear`s with GELU between them and **no activation on the output** (unbounded affine map onto parameter space). Reach it via `probotMakeFlow(..., loc_head = TRUE)` rather than constructing it directly. `forward()` is `base_flow$forward(theta - mu, x)` and `inverse()` is `base_flow$inverse(z, x) + mu`. Key design points: the shift depends on `x`, not `theta`, so `d(theta - mu)/d(theta)` is the identity, the base flow's `log_det_jac` is *already* `log|det dz/dtheta|` with no correction term, and `probotLossNF()` is unchanged and exact (verified to <1e-8 nats against a fresh-graph autograd Jacobian in float64 in `tests/testthat/test-probotFlowLoc.R`). The head buys **credit assignment, not expressiveness** — every conditioner already sees `x`, so a plain flow can represent any conditional shift; what it lacks is parameters whose sole job is that shift. Hence the head should not be added under pure ML (`lambda = 0`), where the optimiser splits head/flow arbitrarily. `location(x)` is public (the trainer and `point_estimate` both read it without an inverse sweep). Store every constructor arg on `self` — `forward()`/`location()` run in a restored function environment at package load where a lexical reference to an argument is not guaranteed to resolve
- **R/probotPredictFlow.R** — `probotSamplePostNF(input, model, n_samples = 5000, col_means, col_sds, col_names, output_dim, device, batch_size, verbose, point_estimate = FALSE)`: draws base N(0,I), applies `model$inverse()`, optionally unscales. Sizes the latent space from `output_dim` **or** `length(col_means)`; errors `"Either 'output_dim' or 'col_means' must be provided."` (and requires `col_sds` whenever `col_means` is given). Vector input or 1-row matrix -> single-obs `(n_samples, output_dim)`; multi-row matrix -> `(n_samples, output_dim, N_obs)` array chunked by `batch_size`. **`class()` of a headed model is `probotFlowLoc` only — it does NOT inherit `probotFlowNSF`/`probotFlowRealNVP`/`probotFlowMAF`**, so any style test written as `inherits(model, "probotFlowNSF")` silently misses it; use `.probotIsFlow()`/`.probotFlowClasses` (which includes `"probotFlowLoc"`). `point_estimate = TRUE` skips sampling entirely and returns one row per input via `.probotFlowPointSummary()`: `mu(x)` when the model has a head, else the `z = 0` inverse — the choice is made by `inherits(model, "probotFlowLoc")`, so the same argument means different things on the two architectures. It needs `output_dim` (or `col_means`) like the sampler, runs inside `with_no_grad()` after the device/scale tensors resolve (so `col_means`/`col_sds` unscale it as usual), ignores `n_samples`/`batch_size`, warns if `verbose` is set, and errors unless `input` is 2-D after vector promotion. A 1-row result matches the corresponding row of a multi-row batch only to float32 kernel noise (measured up to 2.6e-05 relative, not 1e-6 — see the testing convention below) — assert with a tolerance, never `expect_identical`
- **R/probotPredictFlow.R** — `probotSigmaPostNF(input, model, col_means = NULL, col_sds = NULL, col_names = NULL, output_dim = NULL, device = NULL, eps = 1e-3, batch_size = NULL, verbose = FALSE)`** (commit `8536415`) returns `list(post_mean, post_sd)` — a flow's 1-sigma intervals from **one** inverse sweep instead of 5000 samples (measured ~295x faster: 9-parameter ProSpect NSF, 200 observations, CPU). Linearises `theta = f_inverse(z, x)` at `z = 0`: the mean is the centre `f_inverse(0, x)` and `sd_j = ||row_j(J)||` where `J = d theta / d z`, read by central differences over a `2D + 1`-row probe grid per observation (`.probotSigmaGrid()` lays it out **axis-major**, so row `1 + k` is `+eps` on base axis `k` and row `1 + D + k` is `-eps`; row 1 is the unperturbed centre). **Sum over the BASE axis (dim 2 of the `(B, base_axis, parameter)` tensor), never dim 3.** The tempting alternative — sweep `z` along `e_j` and read off `theta_j` — is *not* the marginal scale of `theta_j`: coupling inverses pass half their coordinates through untouched and MAF inverses are triangular, so on the trained 9-parameter ProSpect checkpoint `d theta_j / d z_j` ran 0.008 to -0.21 while off-diagonal entries exceeded 2, and the `e_j` sweep returned half-widths of 0.000–0.21 against sampled 0.7–1.2. `col_means`/`col_sds` follow the sampler exactly (must be given together, length-1 vectors recycle, `var` scales by `sds^2`); a vector or 1-row input returns plain length-`D` vectors. Chunking reuses `.probotFlowActWidth()`/`.probotFlowChunkRows()`, and a `batch_size` above the memory-safe cap is reduced **with a warning that does not change the result** — the probe grid is deterministic, unlike the samplers, so chunk size here affects only speed. **Treat the output as a cheap error bar for ranking and plotting, not a calibrated interval**: it is a first-order local Gaussian, so it carries no skewness or multimodality and is centred on the base-distribution *mode* rather than the mean. Measured against 4000-sample marginal SDs on 60-epoch `D = 3` heteroscedastic flows scored on fresh in-distribution contexts, the delta/sample ratio was tight for two styles (realnvp median 0.95–1.01, maf 1.00) but systematically low for the spline one (**nsf 0.77–0.98**) — its piecewise-linear derivative is the least well approximated by a single local slope. The error is unbounded in general: on the trained ProSpect NSF at random `N(0, I)` contexts the median ratio fell to 0.54 with a 5–95% range of 0.08–2.25, though those contexts are far off the training manifold and inflate the sampling side too. The calibrated route stays `probotSamplePostNF()` scored with `probotPIT()`/`probotCRPS()`/`probotTARP()`. Reached via `.probotFlowPointEstimate(..., point = "grid", z_pts = ...)`, the deterministic generalisation of `"centre"` (one point) and `"mean"` (random points): it returns a 3-D `(n_obs, m, output_dim)` tensor so the caller picks its rank from `point`, and it is deliberately **not** offered by the trainers — their blended MSE term needs one row per observation, and a grid is not a posterior summary. Unlike `probotLossEval()`, it calls `model$eval()` without restoring the prior mode; harmless for flows, which have no dropout or batchnorm. Tests in `tests/testthat/test-probotPredictFlow.R`; docs in `man/probotSigmaPostNF.Rd`
- **R/probotTrainFlow.R** — `probotSingleEpochFlow()` and `probotTrainFlow()`; applies `nn_utils_clip_grad_value_(clip_value = 1.0)` to all three flow styles. Both take `lambda = 0, point = "centre", n_point_samples = 32`, positioned **after** `loss_fn` (all in-tree callers use named args, so the insert is safe). With `lambda > 0` the cost is blended as tensors before `backward()`: `(1-lambda) * loss_fn + lambda * mse`. A flow's forward pass yields latent `z`, not a point estimate, so the MSE target comes from the inverse map via `.probotFlowPointEstimate(model, context, output_dim, point, n_point_samples)`: `"centre"` = `model$inverse(torch_zeros(theta), x)` (deterministic, one sweep, a Jacobian-weighted centre — *not* the posterior mean); `"mean"` = average of `n_point_samples` inverse draws, an unbiased estimate of `E[theta|x]` and the true MDN-`mu_mix` analogue, with MC noise in the estimate and its gradient; **`"loc"` = `model$location(x)`**, the head's own output — one forward through the head, no inverse sweep, so it is deterministic, MC-noise-free, and has no Jacobian-weighting bias, but **requires a model built with `loc_head = TRUE`** and otherwise errors with a message naming `loc_head`. `match.arg` accepts all three in `probotTrainFlow()`, `probotSingleEpochFlow()`, and `.probotFlowPointEstimate()`. `mae`/`rmse` are reported **only** when `lambda > 0`, so the default history stays `epoch,loss` and `lambda = 0` is bit-identical to the pre-blend code (verify with `shuffle = FALSE` — the dataloader iterates from the *global* torch RNG, so two identically-seeded loaders otherwise disagree). `lambda` is validated to be a single non-NA number in [0,1]; `n_point_samples` is validated (whole number >= 1) only when `lambda > 0`. Measured on a learnable synthetic problem the benefit is concentrated in the undertrained regime (5 epochs: centre RMSE 0.79 -> 0.55); by 10+ epochs all lambdas converge to the noise floor. On a skewed (lognormal) posterior each blend favours the estimator it names: `point="mean"` gave posterior-mean RMSE 1.98 vs 2.42 for centre-blend and 3.11 unblended, while the centre estimate was better under centre-blend (2.32 vs 2.92). Cost of `point="mean"` (256-row CPU batch): ~1.5x one inverse sweep at m=32 and ~2.5x at m=128 for realnvp/nsf; ~2x and ~3x for maf. m=32 is a knee — MC deviation of a length-m partial mean from the full-pool mean scales `sqrt(1/m - 1/M)`, so gains flatten past ~32.
- **The `"mean"` tiling invariant**: draws are stacked `(n_obs * m, output_dim)` with each context row repeated `m` times *consecutively*, which is what `theta$reshape(c(n_obs, m, output_dim))$mean(dim = 2)` groups on. Getting this backwards silently trains every observation against the wrong context. Guarded by an echo-stub test in `test-probotTrain.R` (a stub inverse returning its context input must reproduce the context exactly under the group-mean; the wrong grouping must fail).
- **`model$inverse()` is differentiable for all three flow styles**, so gradient-based objectives through the inverse (the `lambda` centre-MSE and mean-of-draws blends) are sound. Confirmed by float64 finite-difference gradient checks (worst relative error ~5e-6), including MAF despite its in-place `theta$narrow(2, i, 1)$copy_(...)`. **When grad-checking `point = "mean"`, use common random numbers** (fix the `z` pool, as the throwaway `meanEstFixedZ` did): the estimator calls `torch_randn()` internally, so autograd and a finite-difference probe otherwise see *different* draws and disagree by O(1) no matter how correct the code is. Two traps when re-running any such check: torch `reshape(-1)` flattens **row-major** while R's `array()`/`matrix()` fill column-major, so probing element `i` by reshaping silently compares the wrong entries — the resulting "worst rel error 1.00" is a broken probe, not a model bug (this happened first). Second, an untrained model's gradients can be legitimately **zero** in whole columns (e.g. a RealNVP conditioner's `theta_1` slice when the input `z` is identically 0), so don't assert "all parameters changed".
- **Do not write accuracy tests for `point` as a race between estimators.** The centre-vs-mean advantage on a skewed posterior needs ~150 epochs (1.38 -> 1.03 RMSE) to clear MC noise; at 30–100 epochs the two trade places across seeds, so such a test is fragile by construction. What the suite does test instead is mechanical and decisive: the tiling invariant, centre determinism vs mean stochasticity, MC concentration under common random numbers (ratio near the theoretical `sqrt((1/m1 - 1/M)/(1/m2 - 1/M))`), per-style trainability, argument pass-through, and `lambda`/`n_point_samples` validation.
- **`point = "loc"` is only *checked* when it is used.** `.probotFlowPointEstimate()` raises the "requires a flow built with loc_head = TRUE" error, but it is called only inside `if (lambda > 0)`. So `point = "loc"` with `lambda = 0` — on a plain flow *or* a headed one — parses through `match.arg()` and then does nothing at all, silently. Same for `point = "mean"` vs an unheaded model: fine, but `n_point_samples` is never consulted. Do not expect the trainer to reject an incoherent `point`/architecture pair up front; it deliberately doesn't, and no test asserts that it does.

  Read it as: **`mu(x)` is the worst estimator in the room** (0.90–0.97 vs Point 0.590 and the *same model's* posterior mean 0.677), and the `lambda` blend moved the head only 0.966 -> 0.897 while making no difference to the posterior mean (0.675 vs 0.677) or to coverage. Coverage is where the head looks *fine*: meanCRPS 0.348/0.348/0.339 and TARP 0.498/0.498/0.497 for the three arms in table order, all sitting on the plain-NSF baseline (0.346/0.497) and inside the MDN's (0.341/0.498); PIT means 0.492/0.502/0.497 vs baselines 0.505 (NSF) and 0.506 (MDN). The density is not damaged by the head — only the point estimate is. The head is not free in parameters (47.2 MB vs 38.5 MB checkpoints) but costs nothing extra in wall time: `nsfloc_*` runs 4.9–6.0 min, i.e. the plain-NSF baseline's 5.1–5.3 min, because `point = "loc"` never runs an inverse sweep — while the *unheaded* `nsf_l30` arm takes 8.1–9.1 min for exactly the opposite reason (`point = "centre"` adds one full inverse sweep per step). So `point = "loc"` is genuinely the cheapest estimator, which is the one prediction the experiment confirmed. **Conclusion for practice: keep `loc_head = FALSE`.** The architecture is sound (the change-of-variables and round-trip tests all pass) but the hypothesis "put the winning regression head inside the flow" fails on this data — the head's MSE-supervised `mu(x)` is worse than the flow's own posterior mean. **Do not reach for `probotSamplePostNF(..., point_estimate = TRUE)` to recover the good number on a headed model — that argument returns `mu(x)`, the bad one.** The 0.677 posterior mean comes from sampling: `apply(probotSamplePostNF(..., n_samples = 2000), c(3, 2), mean)`. So for a point estimate on this data use `probotPredictPoint()`, or a plain flow's `point_estimate = TRUE` (which is then the `z = 0` centre, 0.676 under `nsf_l30`). Do not re-run this experiment expecting a different sign without changing something material (longer training, a wider `lambda` sweep — only 0 and 0.3 were tried, or scoring `mu(x)` against a truth that is itself a posterior mean rather than a single draw). All 9 `.pt` checkpoints, `hist_*.rds`, `evalarm_*.rds` and `covarm_*.rds` are under `scratch/`; the per-parameter physical-RMSE and coverage tables are produced by `scratch/loc_head_report.R`. Note the arms were trained *before* the spline NaN fix (`git 6346bd2`, same day 22:05), and 8 of 9 show 1–5 non-finite loss epochs — so these numbers carry whatever noise that entailed, though the fix is unlikely to flip a 0.3-unit RMSE gap.

### Key conventions
- All model constructors (`probotMakeMDN`, `probotMakePoint`, `probotMakeFlow`), `probotDataLoader`, `probotPredict*`, and `probotLoad*` accept `device = NULL` for auto-detect MPS/CPU
- MDN and Point training use manual gradient clipping via `torch_clamp(param$grad, min=-1, max=1)`; Flow training uses `nn_utils_clip_grad_value_(clip_value = 1.0)` — all three clip, by different mechanisms
- Assessment functions (`probotPIT`/`probotTARP`/`probotCRPS`) operate on R-side objects and take no `device` parameter; `probotSamplePostNF()` does accept `device = NULL` (auto-detects from the model's parameters)
- Training wrappers share `.probotTrainLoop()` for logging, early stopping (`stop_window`, `stop_delta`), and checkpointing
- `probotLossNF` is defined in `probotLoss.R`, not in the Flow file
- Tensors passed to the flow sampler must match the model's device (models auto-place on MPS) — build test tensors with `device = model$parameters[[1]]$device`. This bites any test that calls `model(x)` *directly* to compare against a wrapper that handles placement internally (e.g. the `probotLossEval()` direct-single-batch test), not only the sampler.
- **Never assert cross-shape float32 equality in tests.** torch selects different GEMM kernels per batch shape, so the *same* maths differs by kernel noise: measured 2.6e-05 relative between a 1-row and a 20-row `probotSigmaPostNF()` call, and 1.3e-06 / 2.6e-05 / **6.7e-04** (realnvp / maf / nsf — the spline is noisiest) between its `z = 0` centre and `probotSamplePostNF(point_estimate = TRUE)`. Two `probotSigmaPostNF` tests sat at `tolerance = 1e-5`/`1e-6` and failed on unseeded draws as far back as `8536415`; they now use 1e-3/1e-2 with the measurements recorded in comments. A genuine error (wrong row, wrong axis, row- vs column-norm) is O(1), so a loose tolerance still discriminates — pair it with a negative control like the row-norm-vs-column-norm test rather than tightening.
- Flow style choice: `realnvp`/`nsf` invert in one vectorised coupling sweep (flat cost in `output_dim`); `maf` inverse costs `n_blocks * output_dim` masked MLP evaluations (~2.6x at d=2 rising to ~40x at d=32, measured on CPU)
- **All three styles' reported `log_det_jac` are correct.** Verified against an exact autograd full Jacobian (fresh graph per entry, `qr.R` log-det) across `output_dim` 4/5/9 and 1–8 layers: max disagreement **4.6e-7 nats**. An earlier note claiming RealNVP disagreed by up to 4.7 nats was a *reconstruction artifact* of the test, not a model bug — do not resurrect it. If a Jacobian check ever disagrees by O(1) nats, suspect the check (stale graph, per-column accumulation, wrong `narrow()` slicing) before the model.
- `probotLoad()` returns `list(model, optimizer, metadata)` — `col_means`/`col_sds`/`col_names`/`input_dim`/`output_dim` live under `$metadata`, **not** at the top level. It stores no training data, so a round-trip check on a checkpoint must supply its own (standardised) `theta`/`x` tensors.
- **Prefer float64 when testing NSF/flow invertibility**, and prefer scaling only the conditioner (or a real checkpoint) over `for (p in mdl$parameters) p$mul_(s)` across *all* parameters — the latter reaches regimes no trained model enters and manufactures apparent bugs.
- `probotNetworkSuggest()` (R/probotNetworkSuggest.R) reports flow depth as `n_layers`; its `n_params` heuristic counts exactly `n_layers` MAF blocks, which is why the facade maps `n_layers` -> `n_blocks` rather than ignoring it. Verified **exact** (delta 0) against real parameter counts for Point, MDN and all three flow styles over `output_dim` 2/4/9/200 — the heuristics were never the bug.
- **`probotNetworkSuggest()` returns ONLY constructor fields in the list; `n_params` lives at `attr(s, "n_params")`, never as a list element** (2026-09-06, `.suggest_attach_n_params()` in `R/probotNetworkSuggest.R`). Commit `370d467` ("Don't need the dots anymore") stripped `...` from `probotMakePoint`/`probotMakeMDN`/`probotMakeFlow`, which broke the documented `do.call(probotMakeX, c(s, list(device = "cpu")))()` contract with `unused argument (n_params = ...)` — 9 errors in `test-probotNetwork.R` (5 plug-in + 4 n_params tests; the NSF plug-in test also asserted the count). The attribute is the fix that keeps the strict signatures *and* the direct-splat contract: `...` was removed deliberately (dots re-open the silent partial-matching class that corrupted the realnvp checkpoint metadata), so **do not re-add `...` to those three constructors, and do not put `n_params` back in the returned list**. Consequence for readers: `s$n_params` is silently `NULL` — use `attr(s, "n_params")`; `expect_named()` on the result must not list `n_params`. `man/probotNetworkSuggest.Rd` `\value{}` states this. Guarded by the test "probotNetworkSuggest fields are all accepted by their constructor", which asserts every returned name is in `names(formals())` of the matching constructor across 3 types x 3 styles, so a future report-only field fails there rather than at a user's `do.call()`.

### Documentation notes
- `man/*.Rd` are **hand-maintained**: there are no roxygen `#'` tags in `R/` and no `Roxygen` field in DESCRIPTION, so do not expect `document()`/`roxygenise()` to regenerate them — edit the `.Rd` files directly
- `man/probotAssess.Rd` is the single merged page for `probotCRPS`, `probotPIT`, and `probotTARP`; the separate per-function Rd files were deleted (they never existed in git — the merged page is the only one tracked). Signatures are `input, model, params, n_test = NULL, n_samples = 1e4, col_means = NULL, col_sds = NULL, col_names = NULL, batch_size = NULL, verbose = TRUE`, with no `device` argument; the page documents both MDN and flow usage. The page needs `\alias{probotAssess}` as well as the three function aliases — `man/probotSamplePostMDN.Rd`, `man/probotSigmaPostNF.Rd` and `man/probotMakeMDN.Rd` all `\link{probotAssess}` it, and without the alias `R CMD check` fails "Rd cross-references" (a pre-existing break in the two older pages, fixed 2026-09-12; likewise `\link{torch::nnf_mse_loss}` in `probotLossEval.Rd` does not resolve — use `\link[torch:nnf_mse_loss]{nnf_mse_loss}`). In prose, `\times`/`\eqn` inside `\code{}` triggers an "unknown macro" warning from `Rd2ex`/`checkRd` — use `\eqn{}` for maths in that file
- Flow sampling is seeded by **torch**, not R: `probotSamplePostNF()` calls `torch_randn()`, so a test that must reproduce flow draws has to set `torch::torch_manual_seed()` as well as `set.seed()`. `probotTARP()`'s directions come from R's `rnorm()` *after* the sampler runs, and the flow sampler consumes no R RNG, so the directions can be replayed from a plain `set.seed()` at the same position
- `NAMESPACE` uses `exportPattern("^[[:alpha:]]+")`, so new exported (non-dot) functions need no NAMESPACE edit
- `man/probotFlowLoc.Rd` is the head's page and carries the full rationale (the change-of-variables proof, "what the head buys", reading the point estimate). `probotMakeFlow.Rd` (`loc_head`/`loc_hidden_dims`), `probotTrainFlow.Rd` (a "Point estimators" section covering `"loc"`) and `probotSamplePostNF.Rd` (`point_estimate`) each document their own argument and `\link` back to it — when editing, put the reasoning in `probotFlowLoc.Rd` and only the interface in the other three. Its `\deqn`/`\eqn` blocks are fine; the "unknown macro" trap above only bites inside `\code{}`. Note the source has **no roxygen for it** (consistent with the hand-maintained `man/` rule above), and `tests/testthat/test-probotFlowLoc.R` is its own dedicated file rather than folded into `test-probotNetwork.R`
- `devtools::install()` here (devtools 2.5.0) accepts no `lib`/`prompt`/`...` arguments — use `devtools::install(".", reload = FALSE)`; it installs to `.libPaths()[1]`
- `probotDataLoader(input, output, batch = 1024, shuffle, train_idx, device)` takes `batch` (not `batch_size`) and **inputs before outputs**; `probotTrainFlow()`'s epoch logging fires only on epoch 1 and every `checkpoint_every`, so a quiet multi-epoch run is normal — check `history` rather than assuming it stopped
- Installed ProBot was rebuilt on 2026-09-14 (**0.9.1**) and now carries the model-agnostic assess functions, the spline NaN fix, the constructor convention, the state_dict-derived load path, the inferring `probotSave()`, `probotSigmaPostNF()`, `probotLossEval()`'s `per_row`, the removal of `mdn_components` from every non-constructor signature, the default train/verify split in all three trainers (see the 0.9.0 bullet above), and the `probotLossNF()` (N, N) broadcast fix with the capped verify batch (see the 0.9.1 bullet); `devtools::install()` must be re-run after every source edit, because the installed library and the source tree can diverge silently.
- `.Rbuildignore` excludes `scratch/` (966 MB of experiment checkpoints), `AGENTS.md`, `ProBot.Rcheck/`, built tarballs, `vignettes/*.qmd` and `vignettes/rsconnect/`. Before 2026-09-12 it did **not**, so `R CMD build` produced a 1.1 GB tarball and `R CMD check` copied the whole scratch tree; a pre-existing `ProBot.Rcheck/00check.log` in the repo root was also being swept into builds. Use `R CMD build . --no-build-vignettes` for a fast tarball, and expect two vignette WARNINGs from `R CMD check --no-vignettes` (no rendered HTML in `inst/doc`) that are artifacts of skipping the build, not defects. Note that `pkgload::load_all()` **shadows** the installed package, so `find.package("ProBot")` then reports the *source* directory, not the library — verify with `getNamespaceInfo("ProBot", "path")` in a fresh process (no `load_all`) when confirming what an install actually wrote
- **Never persist a trained model with `saveRDS()`.** Torch tensors serialise as external pointers, so the file loads without error but every call fails with `external pointer is not valid`. Use `probotSave()` (writes `state_dict()` + metadata) and rebuild with `probotLoad()`; plain-R payloads such as `history` data frames are fine to `saveRDS()` separately. Since 0.7.0 `probotSave()` **derives all architecture metadata itself** and rejects the old architecture arguments, so there is nothing left to populate by hand — supply only `col_means`/`col_sds`/`col_names`/`training_history`/`extra_metadata` (see the `R/probotIO.R` bullet).
- **`probotPredictPoint()` returns values in the model's training space**, i.e. already standardised — do not pass its output through `probotScaleForward()`. The MDN/flow samplers are the opposite case: they return *physical* units when given `col_means`/`col_sds`, so they must be re-scaled before comparing against a scaled truth matrix.
- **Never call `lazyLoad()` on the installed `ProBot/R/ProBot` database twice in one session** (and don't mix it with `library(ProBot)`/`load_all()` there): the second open raises `internal error -3 in R_decompress1` / "lazy-load database is corrupt", which then poisons *every* later access to that `.rdb` in the session, including `library(ProBot)` and `pkgload::load_all()`. The install is not actually damaged — a fresh process loads it fine. To inspect installed internals use `Rscript -e` in a subprocess instead. If the running console is already poisoned, the only fix is for the user to restart it; verify code in a subprocess meanwhile
- **After editing a file out-of-band (bash `perl`/`sed`/python), the `read` and `edit` tools serve a STALE CACHE of it** and a later `edit` on the same file can silently revert the out-of-band change (this actually clobbered a `batch_size` insert in `~/Documents/ProSpect_MAF.Rmd`). Either do all edits for a given file through one channel, or re-verify the on-disk content with `awk`/`grep` via bash after mixing methods.
- Files under `~/Documents` are mode `0600`, so the sandboxed `readLines()`/`knitr::purl()` reject them as "not world-readable". The `read`/`edit`/`write` tools work fine; for a *parse* check, `cp` the file to `/tmp` and `chmod 644` the copy first
